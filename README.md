# N-PAS Attendance クラウド版

Google Apps Script（GAS）＋スプレッドシートで動いていた N-PAS 勤怠管理システムを、
**Cloudflare Workers ＋ Cloudflare D1** に移したものです。
スタッフ用の画面は、今の見た目と操作をそのまま引き継いでいます（変わったのはログイン画面の PIN 入力欄の追加だけです）。

> **現在の状態**
> - **本番環境を Vercel に公開済み**：https://npas-attendance.vercel.app/ （本物のデータ用。テスト用アカウントは無効）
> - **テスト環境（試用版）**：https://npas-attendance-trial.vercel.app/ （テスト用データのみ）
> - どちらも開くには Vercel へのログインが必要（後述）。ログインは「名前を選ぶだけ」（AUTH_MODE=name）。
> - 本番用の構成（Cloudflare Workers + D1）のコードも完成済み。Cloudflare への公開は、あなたのアカウントでの操作が必要です（[4章](#4-cloudflare-への公開手順)）。

## 0. Vercel 版（本番・テスト環境）

### 本番環境で試して、終わったら記録を初期化する

1. `https://npas-attendance.vercel.app/admin.html` を開き、「初期設定」で最初の管理者を作る（合言葉は別途お伝えしたもの）。
2. 「スタッフ・PIN」→「スタッフを追加」でスタッフを登録する。または「データ移行・バックアップ」で旧スプレッドシートの名簿・記録を取り込む（5章）。
3. スタッフ画面で、出勤・退勤・申請・一括申請・修正申請・削除申請などを自由に試す。管理画面で承認・集計・申請書を確認する。
4. 試し終わったら、管理画面「データ移行・バックアップ」→「テスト記録の初期化」に「初期化」と入力してボタンを押す。
   - 消えるもの：勤怠記録・修正/削除申請・出勤中の状態・操作履歴
   - 残るもの：スタッフ名簿・管理者
   - 消す前の状態は自動でバックアップされ、「保存されているバックアップ」→「この状態に戻す」で戻せます。
5. 旧スプレッドシートから本物の記録を移す場合は、初期化のあとで「データ移行」を行います。

### 毎日の自動バックアップ
毎日 3:00（日本時間）にデータベース全体を自動保存します（30日分）。管理画面から一覧・ダウンロード・復元ができます。

### テスト環境（試用版）

| 画面 | URL |
|---|---|
| スタッフ画面 | https://npas-attendance-trial.vercel.app/ |
| 管理画面 | https://npas-attendance-trial.vercel.app/admin.html |
| ボタン1つの動作確認 | https://npas-attendance-trial.vercel.app/selftest.html |

- テスト用アカウントは3章と同じです（スタッフ「テスト 一郎」を選ぶだけ／管理者 `testadmin`・`test-password-1234`）。
- 仕組み：画面と API は Cloudflare 版と同じプログラム。データベース（SQLite のファイル）だけを Vercel Blob（非公開）に保存しています（`platform/vercel/handler.mjs`）。書き込みは「誰も更新していないときだけ保存」する条件付き書き込みで、同時に更新された場合は最新を読み直してやり直すため、取りこぼしや二重登録は起きません。
- GitHub の `main` に送ると、自動で公開し直されます。
- アクセス制限（Vercel Authentication）が有効なので、開くには Vercel にログインしている必要があります。他の人にも試してもらう場合は、Vercel のプロジェクト設定 →「Deployment Protection」で「Vercel Authentication」をオフにしてください（テスト用データしか入っていません）。
- この保存方式は、30〜100人程度・同時操作が数人程度の規模を想定しています。大人数が同じ瞬間に操作すると、順番待ち（自動でやり直し）で少し遅くなることがあります。規模が大きくなったら Cloudflare 版（4章）への切り替えをおすすめします（同じプログラムです）。

### ログイン方式
設定 `AUTH_MODE` で切り替えます。`name`＝名前を選ぶだけ（旧システムと同じ。現在の設定）、`pin`＝名前＋PIN。
**名前を選ぶだけの方式は本人確認ではありません**（誰でも他人の名前で打刻・申請できます）。操作はすべて操作履歴に残り、記録の変更・削除は管理者の承認が必要です。

### 勤怠記録の削除申請
スタッフ画面の「打刻修正」で記録を選び、「修正理由」に理由を書いて「この記録の削除を申請する」。管理者が「修正・削除申請」で承認すると削除され、削除前の内容は操作履歴に残ります。

## 1. 構成と、選んだ理由

| 部分 | 使う技術 | 役割 |
|---|---|---|
| 画面 | Workers の静的アセット（`public/`） | HTML・画像・JavaScript を世界中の拠点から配信 |
| サーバー処理 | Cloudflare Workers（`src/`） | 勤怠の保存・取得・認証などの API |
| データベース | Cloudflare D1（SQLite） | スタッフ・勤怠・申請・履歴を保存 |

**選んだ理由**（指示書の選定基準に沿って比較しました）

- **速さ**：Workers は利用者に近い拠点で動き、待ち時間（コールドスタート）がほとんどありません。D1 は SQL のインデックスで「この人・この月」だけを読めるので、データが増えても遅くなりません。
- **データの安全性・整合性**：D1 は SQLite なので、トランザクション（全部成功か全部取り消し）と一意制約（重複を DB が拒否）が使えます。二重出勤・二重登録を DB のレベルで防げます。
- **同時アクセス**：D1 は書き込みを1つずつ順番に処理するため、同時に押されても整合性が崩れません（自動テストで確認済み）。
- **バックアップ**：D1 には「Time Travel」という機能があり、過去の任意の時点に戻せます（無料プランで7日、有料プランで30日）。
- **費用**：このシステムの規模（30〜100人程度）なら **無料プランで収まる見込み**です（Workers 無料プランは 1日10万リクエストまで）。
- **初心者でも管理しやすい**：サーバーの管理（OSの更新など）が不要です。外部パッケージを1つも使っていないので、部品の更新作業もありません。

**検討して選ばなかったもの**：スプレッドシートをそのまま DB として使い続ける（指示書で禁止・遅さの原因）、Supabase など別の DB サービス（Workers と組み合わせると設定と費用が増える）、Durable Objects（D1 で足りるため）。

## 2. 今の仕組みから変わったこと

### 画面（見た目は維持）

- スタッフ画面（`public/index.html`）は、旧 `Index.html` を**機械的に変換**して作りました（変換スクリプト：`tools/convert-original-html.py`）。
- 旧版と新版を同じデータで表示してピクセル単位で比較した結果、**ログイン画面以外の5画面（ホーム・勤怠申請・一括申請・勤務履歴・打刻修正）は完全に一致**しました（差分0ピクセル）。退勤画面はピクセル比較はしていませんが、HTML・CSS は旧版から変更していません。
- **ログイン画面だけ**、名前の選択の下に「🔑 PINを入力してください」の欄を1つ追加しました（本人確認のため）。色・形は既存の入力欄と同じです。
- 埋め込まれていた画像（820KB）を別ファイルにしたので、2回目以降の表示はブラウザのキャッシュを使います。

### サーバー処理

| 旧（GAS の関数） | 新（API） | 主な改善 |
|---|---|---|
| `listStaff` | `GET /api/staff` | — |
| （なし） | `POST /api/login` | **PIN による本人確認**を追加 |
| `clockStatus` | `GET /api/clock/status` | — |
| `clockIn` | `POST /api/clock/in` | 二重出勤を DB の一意制約で防止 |
| `clockOut` | `POST /api/clock/out` | 保存と出勤解除を1つのトランザクションで。再送しても二重登録しない |
| `saveAttendance` | `POST /api/attendance` | 再送しても二重登録しない |
| `getHistory` | `GET /api/history` | 全件読み込み → **この人・この月だけ**をインデックスで取得 |
| `npasSaveBulkAttendance` | `POST /api/bulk` | 重複チェックと登録を1つのSQL文で（同時実行でも重複しない） |
| `npasSubmitCorrection` | `POST /api/corrections` | 「申請中は1記録1件」を DB が保証 |
| `npasUpdateSummaryNow` など | （不要） | 集計表を保存せず、表示のたびに元データから計算（下記） |
| 月別集計シート・個人別シート | 管理画面 | 管理者用の新しい画面（もともと画面がなかったため新規） |
| 打刻修正の承認（シートを手で直す） | 管理画面の「承認」ボタン | 変更前・変更後を操作履歴に自動記録 |

**月別集計の考え方**：旧版は「保存 → 別の通信で集計シートを更新」でした。新版は集計表を持たず、**表示するときに元の勤怠記録から計算**します。インデックスのおかげで1か月・100人分でも数ミリ秒です。これで「保存は成功したが集計が古い」「集計の失敗で保存が失敗扱いになる」ということが起きなくなりました。画面側の集計更新の呼び出しは、通信せずに成功を返すようにしています（見た目と動きはそのまま）。

**勤怠計算のルールは旧版と完全に同じ**です（日付・時刻の形式、翌日退勤、休憩 0〜1439分、小数第2位の丸め、手当の上限100万円、業務内容200文字、24時間以上の打刻は管理者へ連絡）。エラーメッセージも同じ文言です。

## 3. すぐに動作確認する（パソコンだけで動く）

Cloudflare のアカウントがなくても、パソコン上で動かして確認できます（**ローカル模擬環境**。本物の Cloudflare ではありません）。

1. [Node.js](https://nodejs.org/ja) の **22.5 以上**（「LTS」と書かれた版）をインストールします。
2. このフォルダでターミナル（Windows は「PowerShell」）を開き、次を入力します。
   ```
   npm start
   ```
3. ブラウザで次の URL を開きます。
   - スタッフ画面：http://localhost:8787/
   - 管理画面：http://localhost:8787/admin.html
   - **ボタン1つで動作確認**：http://localhost:8787/selftest.html → 「▶ テストを実行」を押すと、主な機能を25項目自動で確認し、✅/❌ で表示します。

**テスト用アカウント**（ローカルとテスト環境だけ。本番では使えません）

| 画面 | 入力するもの |
|---|---|
| スタッフ画面 | 学年「1年生」→ 名前「テスト 一郎」→ PIN `1234` |
| 管理画面 | ログインID `testadmin` ／ パスワード `test-password-1234` |

データは `.local/dev.sqlite` に保存されます。最初からやり直したいときは、このファイルを削除してから `npm start` してください。止めるときはターミナルで `Ctrl + C` を押します。

## 4. Cloudflare への公開手順

> ここからは **あなたの操作が必要** です。費用が発生する操作はありません（無料プランの範囲）。
> まず **テスト環境（staging）** に公開して確認し、問題がなければ **本番環境（production）** に公開します。

### 4-1. 準備（最初の1回だけ）

1. [Cloudflare](https://dash.cloudflare.com/sign-up) のアカウントを作ります（無料）。
2. Node.js 22.5 以上をインストールします（3章と同じ）。
3. このフォルダでターミナルを開き、Cloudflare 公式の道具（wrangler）をインストールします。
   ```
   npm install
   ```
4. Cloudflare にログインします。ブラウザが開くので「Allow（許可）」を押します。
   ```
   npx wrangler login
   ```

### 4-2. テスト環境を作って公開する

1. データベースを作ります。
   ```
   npx wrangler d1 create npas-attendance-staging
   ```
   表示された `database_id = "xxxxxxxx-...."` の値を、`wrangler.toml` の `REPLACE_WITH_STAGING_DATABASE_ID` と置き換えて保存します。
2. 表（テーブル）を作ります。
   ```
   npm run db:migrate:staging
   ```
3. 秘密の値を2つ設定します。まず、ランダムな値を作ります（2回実行して、2つの値を作ってください）。
   ```
   node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
   ```
   1つ目を PIN 用、2つ目を初期設定用の合言葉として設定します（`Enter a secret value:` と聞かれたら貼り付けて Enter）。
   ```
   npx wrangler secret put PIN_PEPPER --env staging
   npx wrangler secret put ADMIN_SETUP_TOKEN --env staging
   ```
   **この2つの値は、パスワード管理アプリなど安全な場所に必ず保管してください。** `PIN_PEPPER` をなくすと、全員の PIN とパスワードの再発行が必要になります。
4. 公開します。
   ```
   npm run deploy:staging
   ```
   初めての公開では、`workers.dev` のサブドメイン（URLの一部になる名前）を決めるよう聞かれることがあります。好きな英数字を入力してください。
   最後に表示される `https://npas-attendance-staging.<あなたのサブドメイン>.workers.dev` が **テスト用URL** です。
5. ブラウザで `テスト用URL/selftest.html` を開き、「▶ テストを実行」を押します。**全部 ✅ になれば、本物の Cloudflare 上で動いています。** 表示される応答時間（ms）が実際の速さです。

### 4-3. 本番環境を作って公開する

4-2 と同じことを、名前を変えて行います。

```
npx wrangler d1 create npas-attendance
（表示された ID を wrangler.toml の REPLACE_WITH_PRODUCTION_DATABASE_ID に貼る）
npm run db:migrate:production
npx wrangler secret put PIN_PEPPER --env production
npx wrangler secret put ADMIN_SETUP_TOKEN --env production
npm run deploy:production
```

> 本番用の `PIN_PEPPER` と `ADMIN_SETUP_TOKEN` は、テスト環境とは**別の値**にしてください。
> 本番環境では、テスト用アカウントとテスト画面の機能は自動的に無効になります。

### 4-4. 最初の管理者を作る

1. `本番URL/admin.html` を開くと「初期設定：最初の管理者を作成」が表示されます。
2. `ADMIN_SETUP_TOKEN` に設定した合言葉、ログインID、名前、パスワード（10文字以上）を入力して「管理者を作成」。
3. 作成後、この初期設定欄は表示されなくなります。2人目以降の管理者は、管理画面の「スタッフ・PIN」→「管理者を追加」から作ります。

### 4-5. 画面やプログラムを更新したとき

```
npm test                  （自動テスト）
npm run deploy:staging    （テスト環境で確認）
npm run deploy:production （本番へ）
```

## 5. データ移行（スプレッドシート → 新システム）

**元のスプレッドシートは一切変更しません**（読み取るだけです）。同じ ID のデータは上書きしないので、**何度実行しても重複しません**。

1. **書き出し**：旧 GAS プロジェクトの `コード.gs` の末尾に `tools/gas-export.gs` の内容を貼り付けて保存し、関数 `npasExportForMigration` を実行します。
   - 実行すると、まず **スプレッドシートのバックアップ（コピー）** がドライブに作られます。
   - 次に、書き出しファイル（`npas-export-日時.json`）がドライブに作られます。実行ログに URL と件数が表示されます。
   - GAS を使わない場合は、各シートを「ファイル → ダウンロード → CSV」で保存しても構いません（複数選択可）。
2. 書き出しファイルをパソコンにダウンロードします。
3. 新システムの管理画面 →「データ移行・バックアップ」→ ファイルを選択。
4. **① 確認のみ**：何も書き込まずに、日付・時刻・数値の変換や重複をチェックします。問題のある行は「シート・行番号・内容」で表示されます。
5. **② 取り込む**：データを入れます。スタッフ名簿 → 勤怠データ → 打刻修正申請 → 修正履歴 の順に処理します。
6. **③ 照合する**：移行元と移行先を1件ずつ比べ、件数と内容が一致しているか確認します。「✅ 問題はありませんでした」と出れば完了です。
7. 実行結果（件数・問題点）は「移行の実行記録」に保存されます。

**移行のルール**

- スタッフID・記録ID・申請IDはそのまま引き継ぎます。
- 名簿にないスタッフIDの勤怠は取り込みません（別のスタッフと混ざらないように）。エラーとして一覧に出ます。
- 勤務時間は**記録されている値をそのまま**使います。再計算した値と違う行は「警告」として表示します（勝手に直しません）。
- 「月別勤怠集計」シートは移行しません（元データから自動で計算されるため）。「個人_」シートも同様です。
- 移行先に同じIDで内容の違うデータがあれば、上書きせず「内容の違い」として報告します。

**移行の後**：スタッフは PIN が未設定なのでログインできません。管理画面の「スタッフ・PIN」→「PIN未設定の人にまとめて発行」で PIN を発行し、本人に配ってください（6章）。

## 6. 普段の運用

| やりたいこと | 操作 |
|---|---|
| スタッフに PIN を配る | 管理画面「スタッフ・PIN」→「PIN発行」（表示は1回だけ。本人に個別に伝える） |
| PIN を忘れた | 同じ画面で「PIN再発行」 |
| PIN を5回間違えてロックされた | 15分待つか、「ロック解除」 |
| 退勤を押し忘れて24時間を超えた | 「スタッフ・PIN」→「出勤を取消」→「勤怠記録」から正しい記録を追加 |
| 修正申請を処理する | 「修正申請」→ 変更前・変更後を確認 →「承認して記録を変更」または「却下」 |
| 月別集計を見る・保存する | 「月別集計」→ 月を選ぶ →「CSVで保存」 |
| 個人別の勤怠申請書を印刷する | 「個人別申請書」→ 人と月を選ぶ →「印刷・PDF保存」 |
| スタッフを追加・卒業 | 「スタッフ・PIN」→「追加」／「編集」で有効をオフ |
| 誰が何をしたか確認する | 「操作履歴」 |
| エラーの詳細を見る | Cloudflare の管理画面 → Workers & Pages → npas-attendance → Logs |

### 本番開始前のテストデータ削除

旧 `npasResetTestHistory` に相当します。**スタッフ名簿と PIN は残し**、勤怠・申請・履歴を消します。

```
npm run backup:production
npx wrangler d1 execute npas-attendance --remote --env production --file scripts/reset-test-history.sql
```

1行目のバックアップが成功したことを確認してから、2行目を実行してください。

## 7. バックアップと復旧

バックアップは3種類あります。

| 方法 | 内容 | 使い方 |
|---|---|---|
| **Time Travel**（自動） | D1 が自動で記録。過去の任意の時点に戻せる | 無料プラン7日・有料プラン30日 |
| **SQL バックアップ** | データベース全体をファイルに保存 | `npm run backup:production` → `backups/` に保存 |
| **管理画面のバックアップ** | 旧シートと同じ列名の JSON（PINは含まない） | 「データ移行・バックアップ」→「バックアップをダウンロード」 |

おすすめ：**月に1回**、SQL バックアップか管理画面のバックアップを保存してください。

### 復旧の手順

- **数日以内の誤操作を戻す（Time Travel）**
  ```
  npx wrangler d1 time-travel info npas-attendance --env production
  npx wrangler d1 time-travel restore npas-attendance --env production --timestamp=2026-11-01T09:00:00+09:00
  ```
  ⚠️ 指定した時点より後の変更はすべて消えます。先に `npm run backup:production` で今の状態を保存してください。
- **SQL バックアップから戻す**：新しいデータベースを作り（4-3 の1行目）、`npx wrangler d1 execute <新しいDB名> --remote --file backups/npas-production-日時.sql` を実行し、`wrangler.toml` の ID を新しい DB に変えて公開します。
- **管理画面のバックアップから戻す**：空のデータベースで、管理画面「データ移行」にバックアップ JSON を選んで取り込みます（PIN は再発行が必要です）。
- **1件の記録の削除を戻す**：「操作履歴」の「管理者による勤怠削除」に削除前の内容がすべて残っているので、「勤怠記録」から追加し直します。

## 8. セキュリティ

**旧システムは名前を選ぶだけで、本人確認がありませんでした。** 新システムでは、名前の選択は本人確認として扱いません。

| 対策 | 内容 |
|---|---|
| 本人確認 | 名前 ＋ **PIN（4〜6桁）**。サーバーは PIN をハッシュ（PBKDF2 ＋ 秘密の値）で保存し、平文は持たない |
| 総当たり対策 | PIN を5回続けて間違えると15分ロック |
| 他人のデータを見られない | サーバーはリクエストのスタッフIDを信用せず、**ログイン時の Cookie で本人を特定**。他人の ID を指定すると拒否（403） |
| 権限の分離 | 管理者は別アカウント（ID＋10文字以上のパスワード）。スタッフの Cookie では管理者 API は使えない |
| セッション | HttpOnly・Secure・SameSite=Strict の Cookie。スタッフ12時間・管理者8時間で失効 |
| CSRF・CORS | 他のサイトからの書き込みは拒否。CORS ヘッダーは返さない（同じURLの画面からのみ利用可） |
| SQL インジェクション | すべてプレースホルダ（`?`）で値を渡す |
| 入力検証 | 画面だけでなくサーバー側で全項目を検証 |
| 画面の保護 | Content-Security-Policy で外部スクリプトを禁止、他サイトへの埋め込み禁止 |
| 秘密の値 | `PIN_PEPPER`・`ADMIN_SETUP_TOKEN` は Cloudflare の secret に保存（コードに書かない） |
| ログ | パス・結果・時間だけを記録。氏名・PIN・勤怠内容はログに出さない。想定外のエラーの詳細は利用者に見せない |
| 操作履歴 | 申請・打刻・承認・修正・削除・PIN発行などをすべて記録（PIN そのものは記録しない） |
| DB の公開 | D1 はインターネットから直接アクセスできない（Workers 経由のみ） |
| テスト機能 | テスト用アカウントとリセット機能は、本番環境では自動的に無効 |

## 9. 速さ

### 測定した結果（ローカル模擬環境・ネットワーク時間を含まない）

`npm run bench` で測定。スタッフ100名、勤怠データ 1,000件／2万件／10万件で比較しました（中央値）。

| 処理 | 1,000件 | 20,000件 | 100,000件 |
|---|---|---|---|
| 月別履歴（1人・1か月） | 0.56 ms | 0.60 ms | 0.55 ms |
| 通常の勤怠申請（保存） | 0.89 ms | 0.95 ms | 0.84 ms |
| 出勤→退勤（2回の合計） | 1.37 ms | 1.41 ms | 1.84 ms |
| 一括勤怠申請（100名） | 2.19 ms | 2.54 ms | 3.24 ms |
| 月別集計（全員・1か月） | 1.09 ms | 1.53 ms | 3.37 ms |
| 個人別勤怠申請書 | 0.64 ms | 0.82 ms | 0.65 ms |
| ログイン（PIN照合） | 4.56 ms | 6.12 ms | 4.31 ms |

**データが100倍に増えても、ほぼ同じ速さ**です（インデックスで必要な行だけを読むため）。

画面の読み込み量：旧版は毎回 **837KB**。新版は初回 645KB、**2回目以降は約45KB**（画像をキャッシュ）。

### まだ測れていないこと（正直に）

- **旧 GAS 版の応答時間**は、旧システムにアクセスできないため測定していません。改善前後の比較は、本番公開後に同じ操作で測る必要があります。
- **Cloudflare 上での実際の応答時間**は未測定です。テスト環境に公開したら、`selftest.html` に各処理の応答時間が表示されます（ネットワーク時間込み）。

## 11. 決めていただきたいこと・残っている課題

### 本番公開の前に決めていただきたいこと

1. **認証の方式**：今は「名前＋PIN（6桁を管理者が発行）」で実装しています。この方式でよいか。
   - PIN を配る手間がかかります。スマホを共用していない前提です。
   - ログイン画面の名簿（名前一覧）は、旧版と同じく誰でも見られます。URL を知っている人に名前が見えてよいか。
   - 名前が分かれば、他人が PIN を5回わざと間違えて15分ロックさせることができます（データは見られません）。
2. **一括勤怠申請を誰に許すか**：旧版どおり「ログインした全員」にしています。代表者だけに絞る場合は、設定 `BULK_POLICY` で一括申請を止めることができます（代表者だけに許す機能は未実装）。
3. **無効にしたスタッフの集計**：旧版どおり、月別集計には「有効」なスタッフだけが出ます。卒業などで無効にすると、過去の月の集計からも消えます（記録自体は残ります）。

### 残っている課題

- Cloudflare への公開と、本物の環境での確認（4章・あなたの操作が必要）
- 旧 GAS 版との速度の比較（公開後に測定）
- 実際のスプレッドシートでの移行の確認（5章。まずテスト環境で試すことをおすすめします）
- 承認時、旧システムから移行した修正申請で「変更前」の情報が欠けている場合は、安全のため承認できません（却下して再申請してもらう）。
- データが非常に多い場合（数万件以上）、無料プランでは「月別集計CSV（全月）」が CPU 時間の制限に近づく可能性があります。その場合は月ごとの CSV を使うか、有料プラン（月5ドル）にしてください。
